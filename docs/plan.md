# 프로젝트 설계: LLM 에이전트의 토큰 공정 혼잡 제어

팀 계획서(11/3)를 코딩용으로 줄인 문서다. 무엇을 만들고 어떻게 비교하는지의 기준이다. 바뀌면 이 문서부터 고친다.

## 1. 문제

LLM API에는 분당 요청 수(RPM), 분당 입력 토큰(ITPM), 분당 출력 토큰(OTPM) 한도가 있다. 하나라도 넘으면 429와 기다릴 초를 알려 주는 `retry-after`가 오고, 서버 전체가 과부하면 529가 온다.

흔한 대응은 동시 요청 수를 고정하고 실패하면 다시 보내는 것이다. 낮게 잡으면 한도가 남고, 높게 잡으면 429와 재시도가 쌓이며, 키 하나를 여러 에이전트가 나눠 쓰면 먼저 많이 보낸 쪽이 한도를 독차지한다. 보낼 수 있는 양을 모르는 채 공유 자원을 나눠 쓰는 문제로, TCP가 풀어 온 문제와 같다.

### LLM이라서 생기는 문제 (보고서 앞부분에 내세울 것)

1. **출력 길이를 미리 모른다.** 토큰 윈도는 출력 토큰을 예상해 예약하고, 끝난 뒤 실제 값으로 정산한다.
2. **지연 신호에 잡음이 크다.** 응답 시간 = 서버 대기 + TTFT + 출력 길이 × 토큰당 시간. 긴 답이 늦은 건 혼잡이 아니므로 지연 기반 제어는 TTFT나 토큰당 시간을 쓴다. 4주차 RTT 추정(EWMA)과 같은 고민이다.
3. **신호가 둘이다.** 429는 "내 한도 초과"(나만 줄이면 됨), 529는 "서버 전체 과부하"(모두가 줄여야 함).
4. **거절이 즉시 온다.** TCP는 손실을 늦게 알지만 429는 바로 오고 `retry-after`가 기다릴 시간까지 알려 준다.

### 연구 질문 (11/17 방향 변경)

> **서버를 고치지 않고, 중앙 조정자 없이, 각 에이전트가 429와 한도 헤더만 보고 제어할 때, 요청 크기가 다른 에이전트들이 토큰 한도를 공정하게 나눠 쓸 수 있는가?**

요청 수로 윈도를 잡는 AIMD(C2)는 요청 수를 공평하게 나눈다. 그런데 한 에이전트는 요청당 100토큰, 다른 에이전트는 1,000토큰을 쓰면 토큰은 10배 차이가 난다. TCP에서 패킷 크기나 RTT가 다른 흐름이 불공정해지는 것과 같은 구조다. 여기에 위 1번(출력 길이를 끝나야 안다)이 겹쳐서, 토큰으로 윈도를 잡으려 해도 보낼 때는 얼마를 쓸지 모른다.

## 2. 가짜 LLM 서버 (P1, `server/`)

텍스트는 만들지 않는다. 한도, 대기열, 지연만 흉내 낸다.

- **한도**: RPM, ITPM, OTPM을 각각 토큰 버킷으로. 버킷이 비면 429 + `retry-after`.
- **처리 용량**: 동시에 처리하는 슬롯 C개. 넘치는 요청은 대기열에서 기다리며 늦어지고(1주차 큐잉 지연), 대기열이 Q를 넘으면 529.
- **응답 시간** = 대기 + TTFT(기본값 + 입력 토큰에 비례) + 출력 토큰 수 × 토큰당 시간.
- **출력 길이**: 요청마다 분포에서 뽑는다. 클라이언트는 응답이 끝나야 안다.
- **남은 한도 헤더**: 응답마다 붙인다(C5용).
- **설정 변경**: 실행 중 한도와 용량을 바꿀 수 있다(E2, E5용).
- **에이전트별 토큰 집계**: `agent_id`별로 쓴 입력·출력 토큰을 남긴다. 토큰 기준 공정성을 서버 쪽에서도 확인하기 위해서다 (E4 핵심).
- **시간 축소**: 분당 한도를 초 단위로 줄여 실험 한 번이 1~2분 안에 끝나게 한다.

## 3. 컨트롤러 (P2, `client/controllers.py`)

| # | 컨트롤러 | 동작 | 역할 |
| --- | --- | --- | --- |
| C0 | 고정 동시성 + 즉시 재시도 | 동시 요청 1·8·32·64개 고정, 실패하면 바로 다시 | 나쁜 기준선 |
| C1 | 고정 + 지수 백오프·지터 | 실패할 때마다 대기 2배, 무작위로 흔듦 | 현업 표준 기준선 (7주차 이진 지수 백오프) |
| C2 | AIMD + 슬로 스타트 (요청 수 윈도) | 처음엔 한 바퀴에 2배, 이후 한 바퀴에 +1, 429면 절반 | 4주차 TCP Reno |
| **C3** | **토큰 가중 AIMD (핵심 제안)** | 윈도를 토큰으로 잡는다. 보낼 때는 출력 토큰을 예상해 예약하고, 끝나면 실제 쓴 토큰으로 정산해 예상값을 고친다 | 연구 질문, LLM 문제 1 |
| C4 | 지연 기반 | TTFT가 최소값 대비 늘면 미리 줄임 (넷플릭스 gradient 방식) | E4 비교군, 4주차 지연 기반 |
| C5 | AIMD + 명시적 신호 | `retry-after`와 남은 한도 헤더를 읽고 미리 맞춤 | E4 비교군, 4주차 ECN |

C0~C2는 기준선, C3가 우리 제안, C4·C5는 비교군이다. C3 설계는 13주차 초에 `docs/controllers.md`에 따로 적는다.

공통 규칙: 같은 바퀴(줄이기 전에 보낸 요청)의 429가 여러 개 와도 한 번만 줄인다. TCP가 한 윈도 안의 여러 손실을 한 번의 혼잡으로 보는 것과 같다.

### C2 참고 구현 (팀 계획서)

```python
class AIMDWindow:
    """동시 요청 수를 TCP의 cwnd처럼 조절한다."""
    def __init__(self, init=1, ssthresh=32, max_window=128):
        self.cwnd = init              # 지금 동시에 보낼 수 있는 요청 수
        self.ssthresh = ssthresh      # 슬로 스타트를 끝낼 기준
        self.max_window = max_window
        self.in_flight = 0            # 응답을 기다리는 요청 수
        self.sent = 0                 # 지금까지 보낸 요청 번호
        self.recover_until = 0        # 이 번호까지는 이미 줄인 바퀴로 본다

    def can_send(self):
        return self.in_flight < int(self.cwnd)

    def on_send(self):
        self.in_flight += 1
        self.sent += 1
        return self.sent              # 요청 번호를 돌려줘 응답과 짝지음

    def on_success(self):
        self.in_flight -= 1
        if self.cwnd < self.ssthresh:
            self.cwnd += 1            # 슬로 스타트: 성공마다 +1 → 한 바퀴에 2배
        else:
            self.cwnd += 1 / self.cwnd  # 혼잡 회피: 한 바퀴에 +1 (덧셈 증가)
        self.cwnd = min(self.cwnd, self.max_window)

    def on_rate_limited(self, req_no):  # 429를 받았을 때
        self.in_flight -= 1
        if req_no <= self.recover_until:  # 같은 바퀴의 429는 한 번만 반영
            return
        self.ssthresh = max(self.cwnd / 2, 1)
        self.cwnd = self.ssthresh     # 절반으로 (곱셈 감소)
        self.recover_until = self.sent  # 지금까지 보낸 요청은 같은 바퀴
```

## 4. 작업량 (P3, `runner/`)

- 에이전트 하나 = 처리할 작업 N개(예: 문서 요약 300건)를 가진 비동기 클라이언트.
- 입력·출력 토큰 길이는 정해진 분포에서 뽑고 시드를 고정해, 모든 컨트롤러가 같은 작업을 받는다.
- **에이전트 종류** (E4용): 가벼운 에이전트(짧은 입력·출력)와 무거운 에이전트(긴 입력·출력)를 섞는다. 무거운 쪽이 요청당 토큰을 약 10배 쓰도록 분포를 정한다. 종류는 요청 로그의 `agent_class`에 남긴다.

## 5. 실험

| 실험 | 조건 | 보는 것 | 연결 개념 | 단계 |
| --- | --- | --- | --- | --- |
| --- | --- | --- | --- | --- |
| E1 단일 에이전트 | 에이전트 1개, 한도 고정, C0~C3 | 처리량, 429 비율, 작업 완료 시간 | 혼잡 제어 기본 | 기준선 |
| E3 같은 크기 공정성 | 같은 크기·같은 컨트롤러 에이전트 2~4개, 늦게 합류 포함 | 각자의 몫, Jain 지수, 수렴 시간 | AIMD 공정성 수렴 | 기준선 |
| **E4 크기가 다른 에이전트** | 가벼운 에이전트와 무거운 에이전트를 같은 서버에. 모두 C2일 때, 모두 C3일 때, (여유 되면) C4·C5 | **토큰 기준 Jain 지수**, 요청 기준 Jain 지수, 전체 처리량, 429 | 패킷 크기·RTT 불공정, Chiu & Jain | **핵심** |
| E6 실제 검증 | 로컬 LLM 서버, 소규모 실제 API로 E4 축소판 | 가짜 서버에서 본 경향이 나오는가 | 가짜 서버의 현실성 | 목표 |
| E2 한도 변화 | 실행 중 한도를 절반으로, 다시 원래대로 | 적응 시간, 그동안의 429 | 슬로 스타트, AIMD 회복 | 여유 |
| E5 서버 과부하 | 한도는 넉넉, 서버 용량이 병목 → 529 | 지연 신호가 529보다 먼저 반응하는가 | 지연 기반 vs 손실 기반 | 여유 |

E4의 예상: C2는 요청 수를 공평하게 나누므로 토큰 기준으로는 무거운 에이전트가 독점한다(토큰 Jain 지수가 낮음). C3는 토큰 기준으로 나누므로 토큰 Jain 지수가 1에 가까워진다. 대신 출력 예상이 틀리는 만큼 처리량이나 429에서 손해가 있을 수 있고, 그 크기를 잰다.

### 지표

- 처리량: 분당 완료 요청 수, 분당 출력 토큰 수, 한도 활용률
- 오류: 429·529 비율, 재시도 횟수
- 지연: 요청 완료 시간 p50·p95, 전체 작업 완료 시간
- 공정성: Jain 지수 = (Σx)² ÷ (n × Σx²), 모두 같으면 1. x를 **완료 요청 수**로 한 것과 **사용 토큰 수(입력 + 출력)**로 한 것을 둘 다 계산한다. E4에서는 토큰 기준이 주 지표다.
- 적응: 한도가 바뀐 뒤 새 수준에 도달하기까지 걸린 시간

## 7. 수업 개념

- 1주차: 큐잉 지연, 처리량, 병목 → 가짜 서버 대기열 모델, 처리량 지표
- 2주차: HTTP 상태 코드와 헤더, 지속 연결 → 429·529, `retry-after`, 클라이언트
- 4주차: cwnd, 슬로 스타트, AIMD, 혼잡 회피, 공정성, 지연 기반 제어, RTT 추정(EWMA), ECN → C2~C5, E3·E4 (패킷 크기·RTT가 다른 흐름의 불공정 → 토큰 크기가 다른 에이전트)
- 5주차: 라우터 큐, 버퍼, 스케줄링 → 서버 대기열과 529 모델
- 7주차: 이진 지수 백오프 → C1과 재시도 정책

## 10. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| "LLM은 그냥 부하일 뿐" 질문 | LLM 문제 4가지를 보고서 앞에, E6 실제 검증 결과를 넣음 |
| "이미 있는 연구 아닌가" 질문 | 1절 관련 연구 표: 중앙 프록시 없음, 토큰 기준, 출력 길이 모름이 차이점 |
| C3가 기대만큼 공정하지 않음 | 출력 예상 오차가 원인인지 따로 잼 (예상 대신 실제 출력 길이를 미리 아는 "정답 C3"와 비교). 안 되면 그 이유 자체를 결과로 |
| 13주차에 C3와 작업량이 동시에 필요 | C3는 P2, 작업량은 P3로 나눠 병렬. 인터페이스(`agent_class`, 토큰 집계)는 이번 주에 먼저 확정 |
| 가짜 서버에서만 된 결과라는 의문 | E6에서 실제 서버의 지연 곡선과 429 동작을 비교, 다른 점은 한계로 밝힘 |
| asyncio가 처음인 팀원 | 10주차에 작은 예제로 익히고, 핵심 로직은 비동기 코드와 분리해 테스트 |
| 지연 잡음으로 C4가 흔들림 | TTFT·토큰당 시간 + EWMA. 그래도 흔들리면 그 자체를 결과로 분석 |
| 실제 API 비용 | 저렴한 모델, 짧은 실행, 비용 상한. 여유 단계라 빠져도 결과는 성립 |
| 일정 지연 | 최소 단계를 12주차까지 끝내는 것을 최우선으로 |
