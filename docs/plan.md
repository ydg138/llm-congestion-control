# 프로젝트 설계: LLM 에이전트 혼잡 제어

팀 계획서(박준영 작성, 11/3)를 코딩용으로 줄인 문서다. 무엇을 만들고 어떻게 비교하는지의 기준이다. 바뀌면 이 문서부터 고친다.

## 1. 문제

LLM API에는 분당 요청 수(RPM), 분당 입력 토큰(ITPM), 분당 출력 토큰(OTPM) 한도가 있다. 하나라도 넘으면 429와 기다릴 초를 알려 주는 `retry-after`가 오고, 서버 전체가 과부하면 529가 온다.

흔한 대응은 동시 요청 수를 고정하고 실패하면 다시 보내는 것이다. 낮게 잡으면 한도가 남고, 높게 잡으면 429와 재시도가 쌓이며, 키 하나를 여러 에이전트가 나눠 쓰면 먼저 많이 보낸 쪽이 한도를 독차지한다. 보낼 수 있는 양을 모르는 채 공유 자원을 나눠 쓰는 문제로, TCP가 풀어 온 문제와 같다.

### LLM이라서 생기는 문제 (보고서 앞부분에 내세울 것)

1. **출력 길이를 미리 모른다.** 토큰 윈도는 출력 토큰을 예상해 예약하고, 끝난 뒤 실제 값으로 정산한다.
2. **지연 신호에 잡음이 크다.** 응답 시간 = 서버 대기 + TTFT + 출력 길이 × 토큰당 시간. 긴 답이 늦은 건 혼잡이 아니므로 지연 기반 제어는 TTFT나 토큰당 시간을 쓴다. 4주차 RTT 추정(EWMA)과 같은 고민이다.
3. **신호가 둘이다.** 429는 "내 한도 초과"(나만 줄이면 됨), 529는 "서버 전체 과부하"(모두가 줄여야 함).
4. **거절이 즉시 온다.** TCP는 손실을 늦게 알지만 429는 바로 오고 `retry-after`가 기다릴 시간까지 알려 준다.

## 2. 가짜 LLM 서버 (P1, `server/`)

텍스트는 만들지 않는다. 한도, 대기열, 지연만 흉내 낸다.

- **한도**: RPM, ITPM, OTPM을 각각 토큰 버킷으로. 버킷이 비면 429 + `retry-after`.
- **처리 용량**: 동시에 처리하는 슬롯 C개. 넘치는 요청은 대기열에서 기다리며 늦어지고(1주차 큐잉 지연), 대기열이 Q를 넘으면 529.
- **응답 시간** = 대기 + TTFT(기본값 + 입력 토큰에 비례) + 출력 토큰 수 × 토큰당 시간.
- **출력 길이**: 요청마다 분포에서 뽑는다. 클라이언트는 응답이 끝나야 안다.
- **남은 한도 헤더**: 응답마다 붙인다(C5용).
- **설정 변경**: 실행 중 한도와 용량을 바꿀 수 있다(E2, E5용).
- **시간 축소**: 분당 한도를 초 단위로 줄여 실험 한 번이 1~2분 안에 끝나게 한다.

## 3. 컨트롤러 (P2, `client/controllers.py`)

| # | 컨트롤러 | 동작 | 역할 |
| --- | --- | --- | --- |
| C0 | 고정 동시성 + 즉시 재시도 | 동시 요청 1·8·32·64개 고정, 실패하면 바로 다시 | 나쁜 기준선 |
| C1 | 고정 + 지수 백오프·지터 | 실패할 때마다 대기 2배, 무작위로 흔듦 | 현업 표준 기준선 (7주차 이진 지수 백오프) |
| C2 | AIMD + 슬로 스타트 (요청 수 윈도) | 처음엔 한 바퀴에 2배, 이후 한 바퀴에 +1, 429면 절반 | 4주차 TCP Reno |
| C3 | AIMD (토큰 윈도) | 진행 중인 토큰 합을 윈도로, 출력 토큰은 예상해 예약 | LLM 문제 1 |
| C4 | 지연 기반 | TTFT가 최소값 대비 늘면 미리 줄임 (넷플릭스 gradient 방식) | 4주차 지연 기반, LLM 문제 2 |
| C5 | AIMD + 명시적 신호 | `retry-after`와 남은 한도 헤더를 읽고 미리 맞춤 | 4주차 ECN과 비교, LLM 문제 3·4 |

공통 규칙: 같은 바퀴(줄이기 전에 보낸 요청)의 429가 여러 개 와도 한 번만 줄인다. TCP가 한 윈도 안의 여러 손실을 한 번의 혼잡으로 보는 것과 같다.

### C2 참고 구현 (팀 계획서)

```python
class AIMDWindow:
    """동시 요청 수를 TCP의 cwnd처럼 조절한다."""
    def __init__(self, init=1, ssthresh=32, max_window=128):
        self.cwnd = init              # 지금 동시에 보낼 수 있는 요청 수
        self.ssthresh = ssthresh      # 슬로 스타트를 끝낼 기준
        self.max_window = max_window
        self.in_flight = 0            # 응답을 기다리는 요청 수
        self.sent = 0                 # 지금까지 보낸 요청 번호
        self.recover_until = 0        # 이 번호까지는 이미 줄인 바퀴로 본다

    def can_send(self):
        return self.in_flight < int(self.cwnd)

    def on_send(self):
        self.in_flight += 1
        self.sent += 1
        return self.sent              # 요청 번호를 돌려줘 응답과 짝지음

    def on_success(self):
        self.in_flight -= 1
        if self.cwnd < self.ssthresh:
            self.cwnd += 1            # 슬로 스타트: 성공마다 +1 → 한 바퀴에 2배
        else:
            self.cwnd += 1 / self.cwnd  # 혼잡 회피: 한 바퀴에 +1 (덧셈 증가)
        self.cwnd = min(self.cwnd, self.max_window)

    def on_rate_limited(self, req_no):  # 429를 받았을 때
        self.in_flight -= 1
        if req_no <= self.recover_until:  # 같은 바퀴의 429는 한 번만 반영
            return
        self.ssthresh = max(self.cwnd / 2, 1)
        self.cwnd = self.ssthresh     # 절반으로 (곱셈 감소)
        self.recover_until = self.sent  # 지금까지 보낸 요청은 같은 바퀴
```

## 4. 작업량 (P3, `runner/`)

- 에이전트 하나 = 처리할 작업 N개(예: 문서 요약 300건)를 가진 비동기 클라이언트.
- 입력·출력 토큰 길이는 정해진 분포에서 뽑고 시드를 고정해, 모든 컨트롤러가 같은 작업을 받는다.

## 5. 실험

| 실험 | 조건 | 보는 것 | 연결 개념 |
| --- | --- | --- | --- |
| E1 단일 에이전트 | 에이전트 1개, 한도 고정, C0~C5 전부 | 처리량, 429 비율, 작업 완료 시간 | 혼잡 제어 기본 |
| E2 한도 변화 | 실행 중 한도를 절반으로, 다시 원래대로 | 적응 시간, 그동안의 429 | 슬로 스타트, AIMD 회복 |
| E3 공정성 | 같은 컨트롤러 에이전트 2~4개, 늦게 합류하는 에이전트 포함 | 각자의 몫, Jain 지수, 수렴 시간 | AIMD 공정성 수렴 |
| E4 혼합 경쟁 | AIMD vs 고정 64, 지연 기반 vs AIMD | 누가 몫을 가져가는가 | Vegas가 Reno에 밀리는 현상 |
| E5 서버 과부하 | 한도는 넉넉, 서버 용량이 병목 → 529 | 지연 신호가 529보다 먼저 반응하는가 | 지연 기반 vs 손실 기반 |
| E6 실제 검증 | 로컬 LLM 서버, 소규모 실제 API | 동시 요청 수에 따른 지연 곡선, 429 동작 | 가짜 서버의 현실성 |

### 지표

- 처리량: 분당 완료 요청 수, 분당 출력 토큰 수, 한도 활용률
- 오류: 429·529 비율, 재시도 횟수
- 지연: 요청 완료 시간 p50·p95, 전체 작업 완료 시간
- 공정성: Jain 지수 = (Σx)² ÷ (n × Σx²), 모두 같으면 1
- 적응: 한도가 바뀐 뒤 새 수준에 도달하기까지 걸린 시간

### 반복과 재현

조건마다 5회 반복해 평균과 표준편차를 보고한다. 스크립트 한 번으로 실행 → CSV → 그래프까지 돌아가야 한다.

## 6. 얻는 것과 잃는 것

| 방식 | 얻는 것 | 잃는 것 | 실험 |
| --- | --- | --- | --- |
| 고정 동시성 (낮게) | 오류 없음, 단순함 | 한도가 남아 작업이 느림 | E1 |
| 고정 동시성 (높게) | 처리량이 한도에 가까움 | 429와 재시도 폭주, 다른 에이전트의 몫을 빼앗음 | E1, E4 |
| 지수 백오프 | 오류가 몰려도 자동으로 흩어짐 | 동시성은 그대로라 한도에 못 맞추고 기다리는 시간이 길어짐 | E1, E2 |
| AIMD | 한도를 모르고도 찾아감, 공정한 몫으로 수렴 | 톱니 모양 때문에 남는 한도, 주기적인 429 | E1, E3 |
| 토큰 윈도 | 길이가 제각각인 요청을 공정하게 셈 | 출력 예상이 틀리면 과하거나 부족, 구현 복잡 | E1, E3 |
| 지연 기반 | 한도·과부하 전에 미리 줄여 429·529가 적음 | 지연 잡음에 흔들림, 공격적인 상대에게 몫을 빼앗김 | E4, E5 |
| 명시적 신호 | 서버가 알려 주는 값으로 빨리 맞춤 | 헤더가 없거나 키를 여럿이 쓰면 믿기 어려움 | E2, E3 |

## 7. 수업 개념

- 1주차: 큐잉 지연, 처리량, 병목 → 가짜 서버 대기열 모델, 처리량 지표
- 2주차: HTTP 상태 코드와 헤더, 지속 연결 → 429·529, `retry-after`, 클라이언트
- 4주차: cwnd, 슬로 스타트, AIMD, 혼잡 회피, 공정성, 지연 기반 제어, RTT 추정(EWMA), ECN → C2~C5, E3~E5
- 5주차: 라우터 큐, 버퍼, 스케줄링 → 서버 대기열과 529 모델
- 7주차: 이진 지수 백오프 → C1과 재시도 정책
