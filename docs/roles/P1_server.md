# P1 서버: 김준수

가짜 LLM 서버를 만든다. 모든 실험이 이 서버 위에서 돌아가므로, 이 파트가 흔들리면 결과 전체가 흔들린다. "실제 API처럼 한도에 걸리고, 붐비면 느려지는 서버"가 목표다.

## 내가 맡는 파일

- `server/token_bucket.py`: 토큰 버킷 (순수 로직)
- `server/mock_llm.py`: aiohttp 서버, 대기열·처리 슬롯, 지연 모델, 429·529, 헤더
- `server/config.py`: 서버 설정 dataclass
- `tests/test_token_bucket.py`, `tests/test_mock_llm.py`

## 주고받는 것

| 방향 | 상대 | 내용 |
| --- | --- | --- |
| 내가 준다 | P2 양동규, P3 박준영 | `POST /v1/messages` API, 429·529, `retry-after`, 남은 한도 헤더 (`docs/week10.md` 인터페이스) |
| 내가 준다 | P3 박준영 | `POST /admin/config` (실행 중 한도·용량 변경, E2·E5용) |

| 같이 맞춘다 | P3 박준영 | E6: 실제 로컬 LLM 서버의 지연 곡선과 가짜 서버 지연 모델 비교 |

인터페이스를 바꿔야 하면 먼저 디스코드 `#개발`에 알리고 `docs/week10.md`를 고친다.

## 발표 때 설명할 수 있어야 하는 것

- **토큰 버킷이 어떻게 한도를 만드나**: 일정 속도로 토큰이 채워지고, 요청마다 꺼내 쓰고, 비면 거절. `retry-after`는 다음 토큰이 찰 때까지의 시간
- **대기열 지연** (1주차): 처리 슬롯이 다 차면 줄을 서고, 줄이 길수록 늦어진다. 지연 = 대기 + TTFT + 출력 길이 × 토큰당 시간
- **429와 529의 차이**: 429는 그 키의 한도 초과, 529는 서버 전체 과부하. 5주차 라우터 버퍼가 넘쳐 버리는 것과 비슷하다
- **왜 가짜 서버인가**: 같은 조건을 그대로 반복할 수 있고 비용이 없다. 대신 현실과 다를 수 있어 E6로 확인한다
- 예상 질문: "출력 토큰은 언제 차감하나?" → 응답이 끝나야 길이를 아니까 끝날 때. 그래서 OTPM은 늦게 반영된다
