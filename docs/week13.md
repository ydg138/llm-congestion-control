### 결정의 근거: E4 사전 실행 (11/22, 참고용)

`light`(입력 100) + `heavy_in`, 3회 × 25초, 두 에이전트가 같이 도는 10~25초 구간만 계산. 5회 정식 실행으로 다시 확인해야 결론으로 쓸 수 있다.

| 병목 | 입력 크기 비 | C2 토큰 Jain | C3 토큰 Jain |
| --- | --- | --- | --- |
| 입력 토큰 한도 | 10배 | 0.972 | 0.986 |
| 입력 토큰 한도 | 100배 | 0.933 | 0.983 |
| 요청 수 한도 | 10배 | 0.605 | 0.621 |

- 입력 토큰 한도가 병목이면 C2도 이미 꽤 공정하다. 무거운 요청이 입력 버킷에 막혀 429를 더 자주 받기 때문으로 추정한다 (정식 실행에서 에이전트별 429로 확인).
- 요청 수 한도가 병목이면 둘 다 불공정하다. 요청 하나가 무거운 쪽이 같은 요청 수로 토큰을 더 쓴다. 클라이언트가 각자 줄이는 방식으로는 이 비대칭을 없애지 못했다 → **한계**.
- 이 사전 실행의 C3는 증가식 결함이 있던 버전이다. 아래 정식 실행에서 결론이 바뀌었다.

### E4 정식 실행 (11/25, C3 증가식 수정 후)

`results/E4_20261125-135130`. 병목 2종 × C2·C3 × 시드 1~5 = 20회, 모두 `completed`·`OK`. 두 에이전트가 같이 도는 구간의 토큰 기준 Jain 지수 (입력 + 출력 토큰).

| 병목 | C2 토큰 Jain | C3 토큰 Jain | 무거운 쪽 토큰 몫 (C2 → C3) | 같이 돈 구간 (C2 / C3) |
| --- | --- | --- | --- | --- |
| 입력 토큰 한도 | **0.961** (0.934~0.995) | 0.829 (0.792~0.862) | 41% → 27% | 26~32초 / 21~23초 |
| 요청 수 한도 | 0.661 (0.651~0.672) | **0.934** (0.853~1.000) | 86% → 61% | 30~32초 / 19~23초 |

- 5회 모두 같은 방향이다. 앞 5초(슬로 스타트)를 빼고 계산해도 순서는 같다.
- **요청 수 병목**: 증가식을 고친 C3가 사전 실행의 한계를 거의 풀었다. 대가로 요청 한도 사용률이 C2 80~84%에서 C3 60~74%로 낮다 (요청 버킷 용량이 10이라 절반으로 줄일 때 비는 양이 크다).
- **입력 토큰 병목**: C3가 C2보다 덜 공정하고 가벼운 쪽으로 치우친다. 무거운 쪽이 429를 더 받는다 (C3 시드 1~4에서 무거운 쪽 54~142회, 가벼운 쪽 5~13회). 버킷에 남은 양이 적을 때 100토큰 요청은 통과하고 1,000토큰 요청만 막히는 서버 쪽 비대칭으로 추정한다. C2에서는 이 치우침이 요청 수 불공정을 상쇄하지만, 윈도를 이미 토큰으로 맞춘 C3에서는 그대로 더해진다 → **한계**.
- 응답 시간은 가벼운 쪽 0.82초, 무거운 쪽 0.92초 정도로 차이가 작아, 입력 병목 결과를 RTT 불공정으로 설명하기는 어렵다.

## E4 서버 설정 (P1 참고)

사전 실행에서 쓴 구조다. 값은 P1이 E1 시간 규모에 맞춰 정한다.

| 설정 | 입력 토큰 병목 | 요청 수 병목 |
| --- | --- | --- |
| 요청 한도 | 넉넉하게 (먼저 차지 않게) | 초당 20건, 용량 10 |
| 입력 토큰 한도 | 이것만 먼저 차게 | 넉넉하게 |

- 측정 구간: 두 에이전트가 같이 도는 구간만 계산한다. 한쪽이 먼저 끝난 뒤의 구간은 공정성 계산에서 뺀다.
