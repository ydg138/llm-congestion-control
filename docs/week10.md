# 10주차: 인터페이스 확정과 가장 작은 연결

## 목표

"429를 받으면 윈도가 절반이 되고, 성공하면 늘어나는 것"이 진짜 HTTP 응답으로 한 번 돌아가게 만든다. 기능은 최소한으로, 네 역할의 코드가 서로 맞물리는지 확인하는 주였다.

## 이번 주에 정한 것

- **인터페이스는 P1 서버 API 2.0을 따른다.** 계획서 초안(`/v1/messages`, `task_id`, `ttft_ms`)과 이름이 달라서, 서버가 아니라 문서를 맞췄다. 확정본은 `docs/interface.md`.
- **컨트롤러 인터페이스에 `on_error` 추가**: 422·타임아웃은 혼잡이 아니므로 윈도를 바꾸지 않는다.
- **`retry_after`는 응답 본문 값을 쓴다**: `Retry-After` 헤더는 1초 이상으로 올림돼 있다.
- **529도 손실로 본다**: C2는 429와 같이 절반으로 줄인다.

## 배운 것

- 서버 예시 설정(지연 약 0.1초, 한도 초당 10건)에서는 적정 동시성이 약 1개라 AIMD 톱니가 보이지 않았다. 처리량 = cwnd ÷ 지연이므로, 지연을 늘려 (한도 × 지연)을 키우자 톱니가 나왔다.
- 같은 설정에서도 429 횟수가 실행마다 크게 달랐다 (148회 vs 308회). 5회 반복이 필요한 이유다.

## 연결 확인 방법

서버, 실행기, 컨트롤러가 합쳐지면 이렇게 돌려 본다.

```
python -m server.mock_llm --config <E1 설정>                          # 터미널 1
python -m runner.run --exp E1 --controller C2 --tasks 100 --seed 1    # 터미널 2
python -m analysis.plot results/<방금 생긴 파일>.csv
```

돌리기 전에 예측을 적는다: "C2면 cwnd가 처음에 2배씩 오르다 429에서 절반이 되고, 이후 톱니 모양." 그래프가 예측과 다르면 그 차이를 주간 보고서에 쓴다.
