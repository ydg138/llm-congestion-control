# C3 설계 초안: 토큰 가중 AIMD (`TokenAIMD`)

11/17 초안. 구현은 `client/controllers.py`의 `TokenAIMD`(PR #12), 설명은 `docs/controllers.md` 7절. 연구 질문은 `docs/plan.md` 1절.

> **11/25 수정**: 처음 초안의 혼잡 회피 식(성공마다 `mss × cost / cwnd`)은 틀렸다. 한 바퀴에 정확히 `cwnd`만큼 성공할 때만 +mss가 되고, 큰 요청이나 윈도에 요청이 하나만 들어가는 경우에는 어긋난다. 아래 3절 4번과 4절 표를 고친 식으로 바꿨다.

## 1. 한 줄 요약

C2의 윈도 단위를 **요청 수 → 토큰 수**로 바꾼다. 보낼 때 토큰을 예약하고, 응답이 오면 정산하고, 성공하면 **모든 에이전트가 한 바퀴에 같은 토큰 양만큼** 윈도를 늘린다. 429·529면 C2처럼 절반으로 줄인다.

## 2. 서버가 토큰을 세는 방식 (서버 코드에서 확인한 사실)

`server/rate_limit.py`의 `MultiQuota`, `server/mock_llm.py`의 `/generate`:

| 시점 | 서버가 하는 일 |
| --- | --- |
| 요청이 들어올 때 | 요청 버킷 1, 입력 버킷 `input_tokens`, 출력 버킷 `max_output_tokens`를 **모두 꺼낼 수 있을 때만** 수락하고 꺼낸다. 하나라도 모자라면 429 (`limited_by`에 어느 버킷인지) |
| 응답이 끝날 때 | 출력 버킷에 `max_output_tokens − 실제 출력`만큼 돌려준다 (정산) |
| 429일 때 | 아무것도 꺼내지 않는다 |
| 200 응답 본문 | `input_tokens`, `output_tokens`, `max_output_tokens`가 다 들어 있다 |

출력 길이는 서버 설정의 `[output_min, output_max]`에서 `workload_id`로 뽑고, `max_output_tokens`로 자른다. **클라이언트는 상한만 정할 수 있고 실제 길이는 모른다.**

## 3. C3 규칙

| 이름 | 뜻 | TCP |
| --- | --- | --- |
| `cwnd` | 토큰 윈도. 동시에 예약해 둘 수 있는 토큰 합의 상한 | cwnd (바이트) |
| `in_flight` | 지금 예약 중인 토큰 합 | 보냈지만 ACK 안 온 바이트 |
| `est` | 이번 요청의 예약량 | 세그먼트 크기 |
| `cost` | 응답이 온 뒤 실제 쓴 토큰 = `input_tokens + output_tokens` | ACK된 바이트 |
| `mss` | 혼잡 회피에서 한 바퀴에 늘리는 토큰 양 (모든 에이전트 같은 값) | MSS |

1. **보내기**: `in_flight + est <= cwnd`이면 보낸다. 단, 예약 중인 것이 하나도 없으면 `est`가 `cwnd`보다 커도 하나는 보낸다 (안 그러면 큰 요청이 영원히 못 나감).
2. **정산**: 응답이 오면(200·429·529·오류 모두) 그 요청의 예약량을 `in_flight`에서 뺀다. 요청 번호별 예약량을 기억해 둔다.
3. **슬로 스타트** (`cwnd < ssthresh`): 성공마다 `cwnd += min(cost, cwnd)` → 한 바퀴에 최대 2배 (큰 요청 하나로 몇 배씩 뛰지 않게).
4. **혼잡 회피**: 바퀴의 **첫 성공**에서만 `cwnd += mss`. 바퀴는 C4처럼 요청 번호로 센다: 성공한 요청 번호가 `round_end`보다 크면 새 바퀴로 보고 늘린 뒤 `round_end = 지금까지 보낸 요청 수`. 그래서 요청 크기·개수와 상관없이 한 바퀴에 정확히 `+mss`.
5. **곱셈 감소**: 429·529면 `ssthresh = max(cwnd / 2, min_cwnd)`, `cwnd = ssthresh`. 같은 바퀴의 손실은 한 번만 (C2의 `recover_until` 그대로). 줄인 바퀴에서는 늘리지 않는다 (`round_end`도 지금까지 보낸 요청 수로).
6. **오류(422·타임아웃)**: 정산만 하고 윈도는 그대로.

### 예약량 `est`를 어떻게 정하나 (세 가지를 비교)

| 변형 | `est` | 장점 | 단점 |
| --- | --- | --- | --- |
| **C3-max** (기본) | `input + max_output_tokens` | 서버가 실제로 꺼내는 양과 같다. 예상 오차 없음 | 실제 출력이 상한보다 훨씬 짧으면 윈도를 낭비 |
| C3-ewma | `input + 지난 출력 길이의 EWMA` (α = 0.125) | 실제 쓰는 양에 가깝게 더 많이 보냄 | 서버는 상한만큼 꺼내므로, 예상보다 429가 늘 수 있음 |
| C3-oracle (비교용) | `input + 실제 출력` (작업량에서 미리 앎) | 출력 길이를 아는 이상적인 경우 | 현실에선 불가능. "모르는 것의 비용"을 재는 기준선 |

"출력 길이를 모른다"는 LLM 문제의 비용 = C3-max·C3-ewma와 C3-oracle의 차이. EWMA는 4주차 RTT 추정과 같은 식이다.

## 4. 왜 토큰 공정해지나

C2는 한 바퀴에 **요청 1개**씩 늘린다. 요청당 1,000토큰인 에이전트는 한 바퀴에 1,000토큰, 100토큰인 에이전트는 100토큰씩 몫이 는다. C3는 둘 다 **`mss` 토큰**씩 는다. 덧셈 증가가 같고 곱셈 감소가 같으면, Chiu & Jain의 그림을 **토큰 축**에 그대로 옮긴 것이 되어 토큰 윈도가 같아지는 쪽으로 모인다.

손계산 예 (mss = 100, 혼잡 회피 중):

| 상황 | 계산 | 결과 |
| --- | --- | --- |
| cwnd = 1,000, 같은 바퀴에서 cost 500인 성공 2번 | 첫 성공 +100, 둘째는 같은 바퀴라 그대로 | 1,100 |
| cwnd = 1,000, 같은 바퀴에서 cost 100인 성공 10번 | 첫 성공만 +100 | 1,100 (요청 크기·개수와 무관) |
| cwnd = 500, cost 10,064인 큰 요청 하나 성공 | 첫 성공 +100 | 600 (처음 식이면 +10,064) |
| 슬로 스타트, cwnd = 1,000, cost 300 성공 | 1,000 + min(300, 1,000) | 1,300 |
| 슬로 스타트, cwnd = 500, cost 1,200 성공 | 500 + min(1,200, 500) | 1,000 (최대 2배) |
| cwnd = 2,000에서 429 | ssthresh = 1,000, cwnd = 1,000 | 절반 |
| in_flight = 0, cwnd = 500, est = 1,200 | 하나도 없으니 보냄 | 보냄 (in_flight = 1,200) |
| in_flight = 1,200, cwnd = 1,500, est = 400 | 1,600 > 1,500 | 못 보냄 |

## 5. 남은 문제: 지연이 다르면 윈도가 같아도 속도가 다르다 (회의 안건)

한도는 **초당 토큰**인데, 윈도가 같아도 처리량 = 윈도 ÷ 지연이다. 서버 지연 모델은

```
지연 ≈ 대기 + base_ttft + input × input_token_seconds + output × output_token_seconds
```

이고, E1 제안 설정(`base_ttft` 0.02, `input_token_seconds` 0.0001, `output_token_seconds` 0.02)에 `output_max`를 1,000으로 키우면 (대기 시간 제외):

| 에이전트 | 요청 | 요청당 토큰 | 지연 | 결과 |
| --- | --- | --- | --- | --- |
| 가벼움 (`light`) | 입력 100, `max_output_tokens` 64 | 약 164 | 약 1.3초 | 기준 |
| **입력이 무거움** (`heavy_in`) | 입력 10,000, `max_output_tokens` 64 | 약 10,064 (약 61배) | 약 2.3초 (약 1.8배) | 토큰 차이가 지연 차이보다 훨씬 크다. C2는 무거운 쪽에 토큰을 몰아주고, C3가 이를 고치는지 본다. **연구 질문의 깨끗한 경우** |
| **출력이 무거움** (`heavy_out`) | 입력 100, `max_output_tokens` 1,000 | 약 608 (약 3.7배, 출력 평균 약 508) | 약 10.2초 (약 7.8배) | 지연 차이가 토큰 차이보다 크다. TCP의 RTT 불공정처럼 지연이 긴 쪽은 한 바퀴가 길어 윈도가 천천히 큰다. C2에서도 무거운 쪽이 **오히려 손해**일 수 있다 |

그래서:

- `docs/plan.md`의 "C2면 무거운 쪽이 독점"은 **입력이 무거운 경우**에만 맞는 예상이다. E4에 두 종류를 다 넣어 확인하자.
- 출력이 무거운 경우까지 맞추려면 윈도가 아니라 **속도**를 같게 해야 한다. 후보: 증가량을 지연에 맞춰 키우기(지연이 긴 쪽은 한 바퀴에 더 많이 늘림), 또는 AWS adaptive처럼 윈도 대신 초당 토큰을 AIMD로 조절(C3-rate). 이건 C3 기본을 E4에서 먼저 보고 정한다.

## 7. 인터페이스 (바뀌는 것)

- 실행기는 `can_send(est_tokens)`, `on_send(est_tokens)`에 `input_tokens + max_output_tokens`를 넘긴다 (`docs/interface.md` 2절, 이미 반영). C3-ewma는 그중 `max_output_tokens` 부분을 자기 예상으로 바꿔 쓴다. 그러려면 C3가 입력 토큰을 따로 알아야 하므로 **`can_send`·`on_send`에 `input_tokens=0`** 인자를 추가했다 (11/18 `on_send`, PR #12·#22에서 `can_send`까지. 모든 컨트롤러가 받고 C3 말고는 무시).
- C3-oracle은 실제 출력 길이가 필요하다. 출력 길이는 서버가 정하지만, 서버의 계산(`server/model.py`)은 (서버 seed, `output_min`, `output_max`, `workload_id`, `max_output_tokens`)만 쓰는 순수 함수다. 그래서 실행기가 같은 서버 설정 파일로 미리 계산해 **`est_tokens = input + 실제 출력`**으로 넘긴다 (P3 제안, 11/18). 인자를 따로 늘리지 않는다. 서버 코드가 main에 들어온 뒤, 실행 중 설정을 바꾸지 않는 실험에서만 쓴다.
- `on_success`는 `resp["input_tokens"] + resp["output_tokens"]`로 `cost`를 계산한다.
- `state()`에 `cwnd`(토큰), `in_flight`(토큰), `ssthresh`, `est_output`(C3-ewma 예상값)을 남긴다. 로그의 `cwnd` 열은 C3만 토큰 단위다.

## 8. 테스트 계획 (손으로 계산한 값)

4절 표의 줄을 그대로 테스트로 만든다 (`tests/test_c3.py`). 그 외:

- `cwnd`가 `min_cwnd` 아래로, `max_cwnd` 위로 가지 않는다
