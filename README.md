# Congestion Control for LLM Agents

**TCP의 AIMD로 LLM API 요청 한도 안에서 처리량과 공정성 지키기**

2026-2 컴퓨터네트워크 팀 프로젝트 · NetDoctors

## 한 줄 요약

여러 LLM 에이전트가 같은 API를 동시에 호출하면 분당 요청·토큰 한도에 걸려 429 오류가 쏟아지고, 한 에이전트가 한도를 독차지하기도 합니다. 이 문제를 TCP 혼잡 제어 문제로 보고, 에이전트의 동시 요청 수를 혼잡 윈도처럼 조절하는 컨트롤러를 만들어 비교합니다.

## TCP와 LLM API의 대응

| TCP | LLM API |
| --- | --- |
| 혼잡 윈도(cwnd) | 동시에 보낼 수 있는 요청 수 또는 토큰 수 |
| ACK | 성공 응답 |
| 손실 (타임아웃, 중복 ACK 3개) | 429, 529 |
| RTT | 응답 시간 (첫 토큰까지 시간, 토큰당 시간) |
| ECN | 남은 한도를 알려 주는 응답 헤더 |
| 여러 흐름이 링크 하나를 공유 | 여러 에이전트가 API 키 하나를 공유 |

## 비교할 컨트롤러

| # | 컨트롤러 | 역할 |
| --- | --- | --- |
| C0 | 고정 동시성 + 즉시 재시도 | 나쁜 기준선 |
| C1 | 고정 + 지수 백오프·지터 | 현업 표준 기준선 |
| C2 | AIMD + 슬로 스타트 (요청 수 윈도) | TCP Reno |
| C3 | AIMD (토큰 윈도) | 출력 길이를 모르는 문제 |
| C4 | 지연 기반 | 지연 기반 혼잡 제어 |
| C5 | AIMD + 명시적 신호 (retry-after, 남은 한도 헤더) | ECN과 비교 |

## 실험

| 실험 | 보는 것 |
| --- | --- |
| E1 단일 에이전트 | 처리량, 429 비율, 작업 완료 시간 |
| E2 한도 변화 | 적응 시간, 그동안의 429 |
| E3 공정성 | 각자의 몫, Jain 공정성 지수, 수렴 시간 |
| E4 혼합 경쟁 | 서로 다른 컨트롤러끼리 누가 몫을 가져가는가 |
| E5 서버 과부하 | 지연 신호가 529보다 먼저 반응하는가 |
| E6 실제 검증 | 로컬 LLM 서버·실제 API가 가짜 서버와 맞는가 |

## 저장소 구조 (계획)

```
├── server/       # 가짜 LLM 서버: 토큰 버킷, 대기열, 지연 모델, 429·529 (P1)
├── client/       # 컨트롤러 C0~C5 (P2)
├── runner/       # 작업량 생성, 조건별 반복 실험, CSV 기록 (P3)
├── analysis/     # 그래프, 통계 (P4)
├── tests/        # 손으로 계산한 값 확인
└── reports/      # 주간 진행 보고서
```

## 일정

| 주차 | 목표 |
| --- | --- |
| 10~12 | 최소 단계: 가짜 서버(요청 한도 + 대기열 + 429), C0·C1·C2, E1, E3 |
| 13~14 | 목표 단계: 토큰 한도와 C3, C4, C5, E2·E4·E5, 로컬 LLM 서버 검증 |
| 15 | 최종 발표(12/8)와 최종 보고서 |

| 역할 | 담당 | 이름 |
